# Performance testing

How jitnodes was measured, the results with the JIT off and on (and per instruction set), and what they do and
do not show.

## What is compared

"JIT off" means `KernelCompiler::setJitEnabled(false)`: the same kernels run on the built-in scalar
interpreter (one element at a time, the reference implementation used by the tests). "JIT on" runs the machine
code generated by asmjit for one of three instruction-set tiers: **sse2** (4 lanes, works on every x86-64 CPU),
**avx2** (8 lanes, the default) and **avx512** (16 lanes, opt-in with `KernelCompiler::setIsa` or
`jitnodesCli --isa avx512`). The interpreter is deliberately simple, so "JIT vs off" is an upper bound on what a
user gains over naive evaluation, not over optimised C++. To keep that honest the kernel table also has a
**native C++** column: a hand-written loop for the same expression compiled by MSVC with `/O2` (SSE2 baseline,
default `/fp:precise`).

## How to reproduce

```
cmake --preset x64-release
cmake --build --preset x64-release
out/build/x64-release/kernelBench.exe        # prints the tables below as markdown
out/build/x64-release/jitnodesCli.exe examples/graphs/wobble.json --profile --isa avx512
```

`--trace FILE` writes the cook as a timeline: open it in `chrome://tracing` or <https://ui.perfetto.dev>. Each row is a thread,
each bar one node (a fused chain is one bar named after its last node). Gaps between bars on a row show where a level waited
for its slowest branch. The `--profile` table reports the same times as sums.

Run it from an otherwise idle machine, in Release (the program prints a warning if it was built without
optimisation). `JITNODES_JIT_LOG=1` dumps the generated assembly.

## Method

- Each cell is the **median of 5 rounds** (3 for the slow interpreter and branch-network rows); a round is the mean
  of several calls after one warm-up call. Network rows include everything a recook does: planning, parameter
  evaluation, copying the input geometry, running the kernel, and updating the cache.
- Kernel rows run in place on 4,194,304 points with two float channels (`x`, `y`). Compile time is the one-time
  cost of building the kernel (cache miss) with the AVX2 tier.
- Network rows edit one parameter before every recook so exactly the dirty chain recooks; the source `line` node
  stays cached. They use the default (AVX2) tier.
- The tables give the **range over three consecutive runs** (min-max) so run-to-run noise is visible. Interpreter
  numbers are stable (about 3 %); sub-millisecond JIT numbers vary by up to about 2x, so differences between the
  memory-bound kernels' columns are not significant.

Parsing is about 12 us per node (30 MB/s), so even the 2646-node graph loads in 31 ms, less than one cook of it; a binary graph
format would save at most a few tens of milliseconds and is not worth the loss of diffable text. The expensive cooks are
the stateful simulations (`reactionDiffusion` 3.5 s, `boids` 0.24 s): those are what a geometry cache would save at every load.
`generate` of 2M points costs 6 ms, so caching it would be slower than recooking (reading 2M x several floats from disk is
not free), and `nebula` at 0.18 s is borderline.

## What the numbers show

- **The JIT removes essentially all interpretation cost.** Simple kernels run 80-250x faster than the interpreter
  and the cost of compiling (about 0.1 ms) is paid back by the first run. A recook of the 3-node chain on 1M points
  drops from about 50 ms to about 2 ms (roughly 20x) with fusion and the JIT.
- **Vectorised math pays off once kernels are compute-bound.** `sin/cos/exp/log/pow` used to have no JIT support
  and ran at interpreter speed (1x). With the polynomial implementations they are 14-19x faster than the
  interpreter on AVX2 and the instruction-set tier matters: sin+cos takes 11.4 ms on SSE2, 4.4 ms on AVX2 and
  3.7 ms on AVX-512 (about 1.2x over AVX2); exp+log+pow 37.7 / 12.9 / 8.5 ms (about 1.5x over AVX2).
- **Memory-bound kernels do not care about the tier.** Arithmetic, conditional and mask kernels move 32 MB per run
  and are limited by memory traffic (probably cache resident on this CPU), so SSE2, AVX2 and AVX-512 are within
  noise of each other for the cheapest kernel and only about 1.5-2x apart for the others. This is why AVX2 remains
  the default: AVX-512 only helps compute-heavy kernels here, and on some Intel CPUs it can cost clock speed.
- **Against compiler-generated code** the gain is modest for simple arithmetic (about 1x) because both versions
  are memory-bound. For the conditional kernel the native loop is 4.5-6x slower only because MSVC does not
  vectorise `std::sqrt` under `/fp:precise` (errno semantics); a `/fp:fast` or hand-vectorised build would close
  most of that gap. Treat "JIT vs native" as "JIT vs a plain `/O2` build", not as a ceiling for static code.
- **Fusion pays off only together with the JIT.** With the JIT: 2.2-2.4 ms unfused vs 1.65-1.9 ms fused (the
  gap shrank from about 2x because unfused nodes no longer copy untouched channels). With the interpreter fusion is about 15 % *slower*
  (49-51 vs 42-44 ms), because the interpreter's cost is per operation and the fused graph does the same work
  plus a bigger working set.
- **Threads help the interpreter more than the JIT.** The interpreter scales about 2.3-2.7x on 4 threads in the
  network tests. With the JIT the recook is dominated by memory-bound work (copying 1M-point geometries and
  merging), so 4 threads give only about 1.4x on the branch network and nothing on the single chain.
- **Copies were the bottleneck, and are mostly gone.** The branch network used to spend 4-6 ms per merge and a full
  geometry copy per kernel node. Copy-on-write attributes (a kernel only clones the channels it writes) and one
  N-ary concat per merge tree cut the 8-branch recook from about 60 to 21 ms on one thread and from about 43 to 17 ms
  on 4 threads. The remaining 4.4 ms merge is the one unavoidable copy of 8M points (about 64 MB written).

## Caveats

- One machine, one compiler, three runs; differences under about 20 % between rows should not be trusted.
- The vector `sin/cos/exp/log/pow` are approximations (accuracy and limits in `docs/design.md`); the interpreter uses
  the C library functions, so the "JIT off" column computes slightly different values for those kernels.
- Sizes were chosen to make times measurable, not to model a workload; geometry in real graphs is usually smaller,
  in which case planning and allocation overhead matter more than the kernels.
- The interpreter baseline is a scalar reference implementation, not an optimised one.
- Not measured: Debug builds, memory-bound sizes well beyond the cache, AArch64, a thread sanitizer run.
